JWT 인증 개념과 PopPang 토큰 처리

JWT로 로그인 상태를 유지하는 원리를 먼저 정리하고, PopPang 앱이 V2 API에서 토큰을 붙이고 갱신하고 저장하는 코드를 따라가요.

기준 브랜치 refactor/#116 V2 마이그레이션 1단계 근거: Projects/ 코드와 Docs/ 문서

1부는 일반론이에요. PopPang 서버가 어떤 서명 알고리즘과 claim을 쓰는지는 이 저장소에 없어서 다루지 않아요. 2부는 Projects/Shared/Core의 실제 코드만 근거로 써요. 코드에서 확인하지 못한 내용은 확인 필요로 표시했어요.

1부 · 개념

01JWT의 구조

JWT(JSON Web Token)는 점(.) 두 개로 나눈 세 조각짜리 문자열이에요. 각 조각은 JSON이나 바이트를 Base64URL로 인코딩한 값이에요.

eyJhbGciOi...(예시 header).eyJzdWIiOi...(예시 payload).c2lnbmF0dX...(예시 signature)

header

서명 알고리즘(alg)과 토큰 종류(typ)를 담아요. 
{ "alg": "HS256", "typ": "JWT" }

payload

누구의 토큰인지, 언제 만료되는지 같은 주장(claim)을 담아요. 
{ "sub": "user-123(예시)",
  "exp": 1700000000 }

signature

앞 두 조각을 서버의 키로 서명한 값이에요. 위조를 막는 부분이에요. 
sign(header + "." + payload)

Base64URL

Base64에서 URL에 문제를 일으키는 +와 /를 -와 _로 바꾸고, 끝의 = 패딩을 뺀 형식이에요. 그래서 토큰을 URL이나 HTTP 헤더에 그대로 넣을 수 있어요.

주의Base64URL은 인코딩이지 암호화가 아니에요. 누구나 header와 payload를 디코딩해서 읽을 수 있어요. 그래서 payload에 비밀번호나 개인정보를 넣으면 안 돼요.

02서명과 검증

서버는 토큰을 받으면 header와 payload로 서명을 다시 계산해서 signature와 같은지 봐요. 한 글자라도 바뀌었으면 서명이 맞지 않아서 거절해요. 이 덕분에 서버는 세션 저장소를 찾지 않고도 토큰만 보고 "우리가 발급한 그대로인지"를 알 수 있어요.

방식예키특징
대칭키 HMACHS256서명과 검증에 같은 비밀키단순하고 빨라요. 검증하는 쪽도 비밀키를 알아야 해요.
비대칭키RS256, ES256개인키로 서명, 공개키로 검증검증하는 서비스가 많아도 개인키는 발급 서버에만 두면 돼요.

검증할 때는 서명뿐 아니라 exp(만료), iss(발급자), aud(대상) 같은 claim도 함께 확인해요. 서명이 맞아도 만료된 토큰은 거절해야 해요.

앱 관점서명 검증은 서버의 일이에요. 앱은 비밀키를 갖고 있지 않아서 토큰을 검증할 수 없고, 검증할 필요도 없어요. 앱에게 토큰은 받은 그대로 보관했다가 헤더에 실어 보내는 불투명한 문자열이에요. PopPang 앱 코드도 토큰을 디코딩하지 않고 String으로만 다뤄요.
확인 필요PopPang V2 토큰이 JWT 형식인지, 어떤 서명 알고리즘을 쓰는지는 저장소에 근거가 없어요. 확인할 곳: 서버 팀 V2 명세(저장소 밖 내부 문서).

03표준 claim

RFC 7519가 정한 등록 claim이에요. 모두 선택 사항이고, 서비스마다 고르는 조합이 달라요. 시간 값은 1970-01-01 UTC부터 센 초(NumericDate)예요.

claim이름뜻
issIssuer토큰을 발급한 주체
subSubject토큰의 주인. 보통 사용자 식별자
audAudience이 토큰을 받아야 하는 대상 서비스
expExpiration Time이 시각 이후로는 거절해요
nbfNot Before이 시각 전에는 거절해요
iatIssued At발급 시각
jtiJWT ID토큰마다 고유한 ID. 재사용 탐지나 폐기 목록에 써요

이 밖에 역할(role)이나 토큰 용도처럼 서비스가 정한 비공개 claim을 더할 수 있어요. PopPang 서버가 어떤 claim을 넣는지는 다루지 않아요(확인 필요).

04Bearer 헤더

토큰은 HTTP Authorization 헤더에 Bearer 방식(RFC 6750)으로 실어 보내요.

GET /api/v2/... HTTP/1.1
Authorization: Bearer eyJhbGciOi...(예시)

Bearer는 "가진 사람"이라는 뜻이에요. 토큰을 가진 사람이 곧 주인으로 취급돼요. 그래서 토큰이 새면 다른 사람이 그대로 쓸 수 있어요. 저장 위치와 로그에 남기지 않는 규칙이 중요한 이유예요.

05Access Token과 Refresh Token을 나누는 이유

서버가 JWT를 서명만으로 검증하면 빠르지만, 한 번 발급한 토큰을 중간에 무르기 어려워요. 만료 전에는 계속 유효해요. 그래서 토큰을 두 가지로 나눠요.

Access TokenRefresh Token
쓰는 곳모든 API 요청토큰 갱신 API 하나
만료짧게길게
노출 빈도요청마다 네트워크를 타요갱신할 때만 보내요
서버 확인보통 서명과 claim만 봐요보통 서버 저장소와 대조해서 폐기 여부를 봐요
새면만료까지 짧은 시간만 악용돼요서버에서 폐기하면 막을 수 있어요

정리하면, 자주 쓰는 토큰은 짧게 살려 새도 피해를 줄이고, 오래 사는 토큰은 드물게 쓰고 서버가 통제해요.

06짧은 만료와 갱신

Access Token이 만료되면 서버는 401을 줘요. 클라이언트는 Refresh Token으로 갱신 API를 불러 새 토큰을 받고, 실패했던 요청을 다시 보내요. 사용자는 이 과정을 모르고 지나가요.

이때 클라이언트가 지켜야 할 것이 있어요.

  • 만료와 다른 401을 구분해요. 서명이 틀렸거나 계정이 정지된 401은 갱신해도 성공하지 않아요.
  • 재요청은 한 번만 해요. 갱신 뒤에도 실패하면 반복하지 않아야 무한 루프가 생기지 않아요.
  • 갱신 요청을 합쳐요. 화면 하나가 API 다섯 개를 동시에 부르면 다섯 요청이 함께 만료될 수 있어요. 갱신을 다섯 번 보내면 안 돼요(회전을 쓰면 특히 그래요).
확인 필요PopPang 토큰의 운영 유효기간은 앱에 하드코딩하지 않아요. 값은 서버 운영 설정에서 확인해야 해요(api-v2-migration.md 정해야 할 것 7번).

07Refresh Token 회전과 재사용 탐지

회전(rotation)은 갱신할 때마다 Refresh Token도 새로 발급하고 이전 것을 폐기하는 방식이에요. Refresh Token 하나는 한 번만 쓸 수 있어요.

재사용 탐지는 회전과 짝을 이뤄요. 이미 폐기된 Refresh Token이 다시 들어오면, 누군가 옛 토큰을 훔쳐 쓰고 있다는 신호로 보고 그 토큰 계열 전체를 폐기해요. 훔친 사람과 진짜 사용자 중 누가 먼저 썼든, 두 번째 사용에서 걸려요.

회전을 쓰면 클라이언트 쪽 부담이 커져요.

  • 갱신 응답으로 받은 새 Refresh Token을 반드시 저장해야 해요. 저장에 실패하면 손에 남은 것은 폐기된 토큰뿐이에요.
  • 동시에 두 번 갱신하면 두 번째 요청이 폐기된 토큰을 보내게 돼요. 재사용 탐지가 있으면 세션 전체가 끊길 수 있어요.
PopPangAccessTokenRefresher에는 "서버는 이미 이전 Refresh Token을 폐기했으므로"라는 주석이 있어요. 앱은 갱신이 Refresh Token을 바꾼다고 전제하고 작성됐어요(17절). 서버가 재사용 탐지까지 하는지는 확인 필요예요.

08용도별 토큰

모든 권한을 가진 토큰 하나로 모든 일을 하면, 그 토큰이 새는 순간 피해가 커져요. 그래서 특정 단계에서만 쓰는 좁은 권한의 토큰을 따로 둬요. 대표적인 예가 가입 전용 토큰이에요.

  1. 소셜 로그인은 성공했지만 아직 가입하지 않은 사용자가 있어요.
  2. 서버는 정식 Access Token 대신 "가입 API만 부를 수 있는" 토큰을 줘요.
  3. 가입을 마치면 정식 토큰 쌍을 주고, 가입 토큰은 버려요.

PopPang V2에도 이런 토큰이 있어요. 문서상 로그인 응답이 가입을 마친 사용자(COMPLETED)에게는 토큰 쌍을, 가입이 필요한 사용자(PENDING)에게는 Signup Token만 줘요. 앱 코드에서는 APIAuthorization.signup과 AuthTokenStorage의 signupToken 키가 이 토큰을 다뤄요.

09토큰을 둘 곳

iOS Keychain

Keychain은 시스템이 암호화해서 보관하는 저장소예요. 앱마다 접근이 나뉘고, 언제 읽을 수 있는지를 항목마다 정할 수 있어요.

kSecAttrAccessible 값읽을 수 있는 때백업으로 다른 기기 이동
WhenUnlocked기기가 잠금 해제된 동안돼요
AfterFirstUnlock재부팅 뒤 처음 잠금 해제한 다음부터돼요
…ThisDeviceOnly위와 같음안 돼요

토큰에는 보통 kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly를 골라요. 백그라운드 요청에서도 토큰을 읽고, 백업으로 다른 기기에 옮겨지지 않게 하려는 선택이에요. PopPang 저장소에 남아 있는 KeychainStore도 이 값을 써요. 다만 지금 토큰 저장에는 쓰지 않아요(20절).

UserDefaults의 위험

일반적으로는 토큰을 UserDefaults에 두지 말라고 권해요.

  • 앱 컨테이너 안의 plist 파일로 저장돼요. 기기 백업이나 탈옥 기기에서 그대로 읽힐 수 있어요.
  • 설정값용 저장소라 읽기 권한을 항목마다 나눌 수 없어요.
  • 디버깅하면서 전체 내용을 출력하는 일이 흔해서 로그에 토큰이 섞이기 쉬워요.

알아 둘 Keychain 특성

  • 앱을 지워도 남아요. 다시 설치하면 이전 계정 토큰이 살아 있을 수 있어요. UserDefaults는 같이 지워지므로, 두 저장소의 상태가 어긋나요.
  • 읽기가 실패할 수 있어요. 재부팅 뒤 첫 잠금 해제 전에 백그라운드로 실행되면 AfterFirstUnlock 항목도 읽지 못해요. "값이 없음"과 "읽지 못함"은 다른 상황이에요.

PopPang은 이렇게 정했어요팀 결정으로 V2 토큰(Access·Refresh·Signup)은 UserDefaults에 저장해요. AuthTokenStorage가 기본값으로 UserDefaultsStore()를 받고, 키는 auth.accessToken, auth.refreshToken, auth.signupToken이에요.

  • 얻는 것: 앱을 지우면 토큰도 함께 지워져요. 세션 정보와 같은 저장소에 있어서, 재설치한 뒤 이전 계정 토큰만 살아남는 문제가 생기지 않아요. UserDefaults는 읽기·삭제가 실패하지 않아서 "읽지 못함"을 따로 다룰 일도 없어요.
  • 잃는 것: 서버 명세는 Keychain 저장을 요구해요. 이 결정은 명세와 달라요. UserDefaults는 암호화하지 않은 plist라서 기기 백업이나 탈옥 기기에서 토큰이 그대로 노출될 수 있어요.

위 일반론이 틀린 것은 아니에요. PopPang은 위험을 알고 재설치 문제를 먼저 피하기로 했어요. 그래서 토큰을 로그와 분석 이벤트에 남기지 않는 규칙이 더 중요해요.

11전체 그림

PopPang은 서버 API를 V1에서 V2로 옮기는 중이에요. V2부터 토큰 인증이 들어와요. 1단계(#116)는 모든 V2 API가 함께 쓸 네트워크 기반을 Core에 만드는 단계예요. 이 단계에서는 어떤 API도 V2로 바꾸지 않아서 앱 동작은 그대로예요.

Storing, UserDefaultsStoreLocalStorage/Store/토큰을 실제로 담는 UserDefaults 읽기·쓰기·삭제
KeychainStoring, KeychainStoreLocalStorage/Store/Keychain/Keychain 구현. 지금은 토큰 저장에 쓰지 않아요

책임은 이렇게 나뉘어요. plugin은 헤더만 붙이고, 재요청 판단은 asyncRequest가, 갱신은 refresher가, 토큰의 원자적 변경은 storage가 해요.

12API 버전과 인증 종류

API target은 BaseAPI를 채택하고 버전과 인증 종류를 정해요. 기본값은 .v1, .none이에요. 그래서 기존 target은 아무것도 바꾸지 않아도 예전과 똑같이 동작해요.

Projects/Shared/Core/Sources/Network/BaseAPI.swift 
public enum APIAuthorization: Sendable {
    /// 헤더를 보내지 않는다. V1 API와 V2 공개 API(소셜 로그인, 토큰 갱신)가 해당한다.
    case none
    /// `Bearer {accessToken}`을 보낸다.
    case access
    /// `Bearer {signupToken}`을 보낸다. V2 회원가입 API에만 쓴다.
    case signup
}

/// 실제로 적용할 인증 종류. V1 요청에는 서버 계약상 `Authorization` 헤더를 보내지 않는다.
var resolvedAuthorization: APIAuthorization {
    apiVersion == .v1 ? .none : authorization
}

V1 요청에 헤더를 붙이지 않는 이유

  • 서버 계약이에요. 코드 주석과 마이그레이션 문서 모두 "V1 요청에는 Authorization 헤더를 보내지 않는다"고 정해요. V1은 토큰 인증을 쓰지 않아서 헤더가 필요 없어요.
  • 실수를 구조로 막아요. V1 target에 실수로 .access를 적어도 resolvedAuthorization이 .none으로 바꿔요. 토큰이 필요 없는 곳에 토큰을 보내지 않고, V1의 401이 갱신 흐름에 들어가지도 않아요.
  • 전환 중 공존이 안전해요. V1과 V2 호출이 한 앱에 같이 있는 동안, 버전 하나만 보고 인증 경로가 갈려요.

갱신 API와 소셜 로그인처럼 V2지만 토큰 없이 부르는 공개 API도 .none이에요. 갱신 API에 만료된 Access Token을 붙여 보낼 이유가 없어요.

버전별 기본 URL

Projects/Shared/Core/Sources/Network/NetworkConfig.swift 
public static func apiURLString(for version: APIVersion) -> String {
    "\(serverURLString)/api/\(version.rawValue)"   // https://poppang.co.kr/api/v1, /api/v2
}

V2 경로는 V1 경로의 숫자만 바꾼 것이 아니에요. 사용자 종속 API는 경로의 {userUuid}가 빠져요. 사용자를 토큰으로 식별하기 때문이에요(api-v2-migration.md 기본 원칙).

13응답과 오류 코드

V2 성공 응답 가운데 일부는 APIResponse로 감싸져 와요. 감싸는지는 API마다 달라서 모든 응답에 일괄 적용하지 않아요. 실패 응답 형식은 V1과 V2가 같아요.

Projects/Shared/Core/Sources/Network/APIResponse.swift 
public struct APIResponse<T: Decodable>: Decodable {
    let success: Bool; let code: Int; let message: String; let data: T
}
public struct ErrorResponse: Decodable { let success: Bool; let code: Int; let message: String }

HTTP 401만으로는 만료인지 알 수 없어요. 그래서 실패 본문의 서버 에러 코드를 읽어요.

Projects/Shared/Core/Sources/Network/NetworkError.swift 
/// 본문에 정수 `code`가 없으면(5xx 기본 오류 본문 등) `nil`이다.
public var serverErrorCode: Int? {
    case let .invalidStatusCode(_, message):
        return try? JSONDecoder().decode(ServerErrorCodeBody.self, from: Data(message.utf8)).code
}

var isExpiredToken: Bool {
    statusCode == 401 && serverErrorCode == ServerErrorCode.expiredToken   // 5002
}
  • code만 디코딩해요. ErrorResponse 전체를 디코딩하면 message 같은 다른 필드가 빠졌을 때 코드까지 잃어요. 갱신 여부를 가르는 값은 코드 하나라서 그것만 읽어요.
  • 본문 형식이 다르면 nil이에요. 게이트웨이가 만든 5xx 기본 오류처럼 JSON이 아니면 서버 코드 없이 HTTP 상태로만 처리해요.
  • 401과 5002를 함께 봐요. 앱이 따로 처리하는 서버 코드는 지금 expiredToken = 5002 하나예요. 다른 401 코드의 뜻은 이 저장소에 적혀 있지 않아요(테스트는 5001, 5003 등을 "5002가 아닌 401"의 예로만 써요).

14헤더를 붙이는 plugin

AuthenticationPlugin은 Moya의 PluginType이에요. 요청이 나가기 직전 prepare에서 인증 종류에 맞는 토큰을 AuthTokenStorage(UserDefaults)에서 읽어 헤더를 붙여요.

Projects/Shared/Core/Sources/Network/Auth/AuthenticationPlugin.swift 
/// 요청에 담을 토큰. 인증이 필요 없는 요청이거나 토큰이 없으면 `nil`이다.
func token(for target: TargetType) -> String? {
    switch Self.authorization(of: target) {
    case .none:   return nil
    case .access: return storage.loadTokens()?.accessToken
    case .signup: return storage.loadSignupToken()
    }
}

static func authorization(of target: TargetType) -> APIAuthorization {
    let target = (target as? MultiTarget)?.target ?? target
    return (target as? BaseAPI)?.resolvedAuthorization ?? .none
}
  • 매 요청마다 저장소를 읽어요. 갱신 직후의 요청은 자연스럽게 새 토큰을 담아요. 따로 메모리 캐시를 두지 않아요. UserDefaults는 프로세스 안에서 값을 캐시해서, Keychain을 매번 읽을 때보다 부담이 작아요.
  • 읽기는 실패하지 않아요. UserDefaults에서 토큰을 읽는 함수는 throws가 아니에요. 토큰이 없을 때만 헤더 없이 보내요.
  • MultiTarget을 벗겨요. MoyaProvider<MultiTarget>으로 감싼 target이 들어와도 안쪽 target을 꺼내 인증 종류를 봐요. 테스트도 두 경우를 함께 확인해요.
  • plugin은 재요청하지 않아요. Moya plugin에는 응답을 보고 요청을 다시 보내는 기능이 없어요. 재요청은 asyncRequest가 plugin을 찾아서 해요.
  • plugin은 NetworkProvider(authentication:)로 넣어요. nil이면 어떤 요청에도 헤더를 붙이지 않아요. 앱에서는 AppBootstrap이 NetworkProvider.shared.configureAuthentication(_:)으로 넣어요(22절).

15요청 흐름과 한 번만 재요청

MoyaProvider.asyncRequest(_:)가 갱신과 재요청을 맡아요. 아래 그림은 요청 하나가 거치는 길이에요.

Projects/Shared/Core/Sources/Network/MoyaProvider+Async.swift 
switch try await sendAccessRequest(target, authentication: authentication) {
case let .success(response):
    return response
case let .rejectedWithStaleToken(_, error):
    // 보낸 뒤에 갱신·로그인으로 다른 토큰이 저장됐어요. 새 토큰으로 한 번 다시 보내요
    return try await retryAccessRequest(target, authentication: authentication, originalError: error)
case let .expired(sentAccessToken, expiredError):
    do {
        _ = try await authentication.refresher.refreshAccessToken(expired: sentAccessToken)
    } catch let error as AuthSessionError {
        throw error              // 다시 로그인해야 해요
    } catch {
        throw expiredError       // 원래 요청의 401 5002
    }
    return try await retryAccessRequest(target, authentication: authentication, originalError: expiredError)
}

// 다시 보낸 요청이 또 실패하면 갱신하지 않고 그 오류를 던져요
func retryAccessRequest(_ target: Target, authentication: AuthenticationPlugin, originalError: NetworkError) async throws -> Response {
    switch try await sendAccessRequest(target, authentication: authentication) {
    case let .success(response):
        return response
    case let .expired(_, error), let .rejectedWithStaleToken(_, error):
        throw error
    }
}

왜 이렇게 했나요

  • 5002일 때만 갱신해요. 갱신은 만료라는 한 가지 원인만 고쳐요. 다른 401에 갱신하면 성공할 수 없는 요청을 반복하고, 갱신 API 호출만 늘어요.
  • 재요청은 구조상 한 번이에요. retryAccessRequest 안의 두 번째 sendAccessRequest가 .expired나 .rejectedWithStaleToken을 돌려주면 갱신하지 않고 던져요. 반복문이 없어서 무한 재시도가 생길 수 없어요. 이때 토큰은 지우지 않아요. 명세가 이 경우를 정하지 않았기 때문이에요.
  • 보낸 토큰을 응답에서 꺼내요. response.request?.bearerToken으로 실제로 실었던 토큰을 읽어요. 지금 저장된 값이 아니라 "이 요청이 썼던 값"이 있어야 다른 요청이 이미 갱신했는지 판단할 수 있어요(16절).
  • 갱신 실패의 오류를 구분해요. 로그인이 필요하면 AuthSessionError.loginRequired를, 일시적인 실패(400, 403, 429, 5xx, 네트워크)면 원래 요청의 5002 오류를 던져요. 일시 실패에는 토큰을 지우지 않아서 다음 요청이 다시 갱신을 시도해요. 이 정책은 아직 확정이 아니에요(정해야 할 것 3번).
  • 403에는 갱신하지 않아요. 403은 "누구인지는 알지만 권한이 없다"는 뜻이라 토큰을 바꿔도 결과가 같아요.
  • signup API의 5002도 갱신하지 않아요. 첫 guard가 .access만 갱신 흐름에 들여보내요. Signup Token이 만료되면 소셜 로그인부터 다시 해요.
주의갱신과 재요청은 asyncRequest 계열 함수 안에서만 일어나요. Repository가 provider.request의 callback을 직접 부르면 갱신되지 않아요. Alamofire AuthenticationInterceptor를 쓰면 모든 경로에 적용되지만, 401 본문의 서버 코드로 갱신 여부를 나눠야 해서 직접 구현했어요(api-v2-migration.md).

16동시 만료를 갱신 하나로

화면이 여러 API를 동시에 부르면 요청 여러 개가 거의 같은 순간에 5002를 받아요. AccessTokenRefresher는 actor와 진행 중인 Task 하나로 이 갱신을 합쳐요.

Projects/Shared/Core/Sources/Network/Auth/AccessTokenRefresher.swift 
public func refreshAccessToken(expired expiredAccessToken: String?) async throws -> String {
    // ① 다른 요청이 이미 갱신했으면 저장된 새 토큰을 써요
    if let expiredAccessToken,
       let currentAccessToken = storage.loadTokens()?.accessToken,
       currentAccessToken != expiredAccessToken {
        return currentAccessToken
    }
    // ② 갱신이 진행 중이면 그 결과를 기다려요
    if let inFlightRefresh {
        return try await inFlightRefresh.value
    }
    // ③ 처음 온 요청만 갱신 Task를 만들어요
    let task = Task { [storage, refresh] in
        try await Self.performRefresh(storage: storage, refresh: refresh)
    }
    inFlightRefresh = task
    defer { inFlightRefresh = nil }
    return try await task.value
}

왜 이렇게 했나요

  • actor가 상태를 지켜요. inFlightRefresh를 읽고 쓰는 코드는 actor 안에서 한 번에 하나씩만 실행돼요. "Task가 없으면 만든다"를 두 요청이 동시에 통과하는 일이 없어요.
  • actor는 await에서 다른 호출을 받아요(재진입). A가 task.value를 기다리는 동안 B와 C가 들어와 ②에서 같은 Task를 기다려요. 이 재진입 덕분에 갱신이 하나로 합쳐져요.
  • ①이 늦게 온 요청을 처리해요. 갱신이 끝나고 inFlightRefresh가 비워진 뒤에 옛 토큰의 5002가 도착할 수 있어요. 저장된 토큰이 보낸 토큰과 다르면 이미 갱신된 것이라 다시 갱신하지 않아요. 회전 환경에서 폐기된 Refresh Token을 보내는 일을 막아요.
  • 보낸 토큰을 모르면(nil) 갱신해요. 비교할 근거가 없는데 "누가 갱신했겠지"라고 넘기면, 실제로는 아무도 갱신하지 않았을 때 요청이 실패만 하고 끝나요.
  • Task가 실패하면 기다리던 요청도 같은 오류를 받아요. defer로 Task를 비워서 다음 만료 때는 새로 시도해요.

17늦은 응답·로그아웃·재로그인

갱신 요청이 서버에 가 있는 동안 사용자가 로그아웃하거나 다른 계정으로 다시 로그인할 수 있어요. 그다음에 옛 갱신 응답이 도착하면 어떻게 할까요? 그대로 저장하면 지운 세션이 되살아나거나 새 로그인 토큰이 덮여요.

그래서 AuthTokenStorage는 "저장된 값이 내가 아는 값일 때만 바꾸거나 지우는" 함수를 lock 하나로 묶어 제공해요. 비교와 변경 사이에 다른 스레드가 끼어들 수 없어요.

Projects/Shared/Core/Sources/LocalStorage/Storage/AuthToken/AuthTokenStorage.swift 
/// 같은 저장 수단을 쓰는 모든 인스턴스가 함께 쓰는 lock
private static let lock = NSRecursiveLock()

public func replaceTokens(_ tokens: AuthTokens, ifRefreshTokenIs expectedRefreshToken: String) throws -> Bool {
    try withLock {
        guard loadTokens()?.refreshToken == expectedRefreshToken else { return false }
        try saveTokens(tokens)
        return true
    }
}
  • lock이 static이에요. AuthTokenStorage는 struct라 여러 인스턴스가 생길 수 있어요. 실제 저장소(UserDefaults의 같은 키)는 하나라서 lock도 하나를 같이 써요. 저장 수단이 바뀌어도 이 이유는 그대로예요.
  • UserDefaults만으로는 부족해요. UserDefaults의 읽기·쓰기 하나하나는 스레드에 안전하지만, "비교한 뒤 바꾸기"를 한 덩어리로 해 주지는 않아요. 그래서 저장 수단이 바뀌어도 lock과 조건부 함수는 남겼어요.
  • NSRecursiveLock이에요. replaceTokens 안에서 다시 lock을 잡는 loadTokens와 saveTokens를 불러요. 같은 스레드가 lock을 다시 잡아도 멈추지 않아야 해요.

상황별 처리

상황쓰는 함수결과
갱신 성공, 그사이 변화 없음replaceTokens(_:ifRefreshTokenIs:) → true새 토큰을 저장하고 새 Access Token을 돌려줘요
갱신 중 로그아웃같은 함수 → false저장하지 않아요. 저장된 토큰이 없으니 loginRequired
갱신 중 재로그인같은 함수 → false덮어쓰지 않고 재로그인한 Access Token을 써요
갱신 API가 401, 그사이 재로그인removeTokens(ifRefreshTokenIs:) → false새 로그인 토큰을 지우지 않고 그 Access Token을 써요
갱신 API가 401, 변화 없음같은 함수 → true지우고 loginRequired
옛 토큰으로 보낸 요청이 다른 401removeTokens(ifAccessTokenIs:) → false그사이 갱신된 새 토큰을 지우지 않고, 새 토큰으로 원래 요청을 한 번만 다시 보내요(rejectedWithStaleToken)
갱신은 됐는데 저장 실패replaceTokens가 throw남은 옛 토큰을 지우고 loginRequired

마지막 줄이 회전과 관련 있어요. 서버는 갱신하면서 이전 Refresh Token을 이미 폐기했어요. 새 토큰을 저장하지 못했다면 앱에 남은 것은 쓸 수 없는 토큰이에요. 남겨 두면 다음 요청마다 갱신이 실패하니 지우고 로그인을 요구해요.

UserDefaults는 문자열 저장이 사실상 실패하지 않아서 이 줄은 거의 일어나지 않아요. 그래도 catch의 storage.removeTokens() 정리 코드는 그대로 두기로 했어요. 저장 함수(saveTokens, replaceTokens)는 throws라서, 실패했을 때 폐기된 토큰을 남기지 않는 쪽이 안전해요.

AccessTokenRefresher.swift · performRefresh 
catch let error as NetworkError where error.statusCode == 401 {
    // 갱신하는 동안 재로그인으로 토큰이 바뀌었으면 새 토큰을 지우지 않는다.
    if storage.removeTokens(ifRefreshTokenIs: refreshToken) {
        throw AuthSessionError.loginRequired
    }
    return try replacedAccessToken(in: storage)   // 재로그인한 토큰을 따라요
}

저장된 Refresh Token이 서버가 거절한 그 토큰이면 지우고(true) loginRequired를 던져요. 그사이 재로그인으로 다른 토큰이 저장돼 있으면(false) 지우지 않고 그 새 토큰을 따라가요. Access Token 없이 Refresh Token만 남아 있어도 같은 방식으로 비교해요.

토큰 쌍이 다 갖춰지지 않은 상태(예: Refresh Token만 남음)는 로그아웃 상태로 봐요. 이 상태를 만나면 removeIncompleteTokens()가 lock 안에서 "쌍이 정말 없는지" 확인하고 남은 토큰을 지워요. 그사이 로그인으로 쌍이 생겼으면 지우지 않고(false) 그 새 토큰을 써요. 확인과 삭제를 따로 하면 그 사이에 로그인한 토큰을 지울 수 있어서, 한 번에 처리해요.

18Keychain을 쓰면: 실패는 토큰 없음이 아니에요

지금 토큰 저장소는 UserDefaults라서 읽기와 삭제가 실패하지 않아요. 그래서 AuthTokenStorage에서 throws는 저장 함수에만 남기고, 읽기·삭제 실패 처리는 지웠어요. 이 절은 Keychain을 다시 쓰게 될 때 그 처리가 왜 필요한지 정리해요.

저장소에 남아 있는 KeychainStore는 "값이 없음"과 "읽지 못함"을 다르게 돌려줘요.

Projects/Shared/Core/Sources/LocalStorage/Store/Keychain/KeychainStore.swift 
switch status {

이 구분이 필요한 이유는 iOS의 실행 조건 때문이에요. 기기를 재부팅하고 아직 잠금 해제하지 않았는데 푸시 같은 이유로 앱이 백그라운드에서 깨어나면, Keychain을 읽지 못할 수 있어요. 이것을 "토큰 없음"으로 처리하면 멀쩡한 사용자를 로그아웃시켜요.

Keychain으로 되돌린다면 아래 지점에서 읽기 오류를 따로 처리해야 해요. 지금 코드에는 이 처리가 없어요. UserDefaults는 읽기·삭제가 실패하지 않아서, AuthTokenStorage의 읽기·삭제 함수에서 throws를 지웠기 때문이에요.

지점Keychain을 쓸 때 해야 할 처리
AuthenticationPlugin.token(for:)읽지 못하면 헤더 없이 보내고, 401을 받아도 토큰이 없다고 단정하지 않아요
토큰 없이 보낸 요청의 401남은 토큰이 있는지 확인하지 못하면 지우지 않고 받은 오류를 던져요

지금은위 처리를 만들던 코드와 테스트(Keychain 읽기·삭제 실패)는 지웠어요. Keychain으로 되돌리면 AuthTokenStorage 함수에 throws를 다시 붙이고, 이 처리와 테스트를 다시 만들어야 해요(20절).

19Refresh Token을 먼저 저장하는 이유

UserDefaults도 Keychain도 두 키를 한 번에 쓰는 트랜잭션이 없어요. 토큰 쌍을 저장하다 중간에 실패할 수 있어요. 그래서 saveTokens는 하나라도 실패하면 둘 다 지워요. 그런데 지우는 것까지 실패하면 한쪽만 새 값으로 남아요. 어느 쪽이 남는 게 나을까요?

AuthTokenStorage.swift · saveTokens 
/// 새 토큰 쌍을 함께 저장한다. 하나라도 저장하지 못하면 둘 다 지운다.
///
/// Refresh Token을 먼저 쓴다. 지우는 것까지 실패해 한쪽만 남더라도 새 Refresh Token과 옛 Access Token이 남아,
/// 옛 Access Token이 만료되면 새 Refresh Token으로 다시 갱신할 수 있다.
public func saveTokens(_ tokens: AuthTokens) throws {
    try withLock {
        do {
            try store.set(tokens.refreshToken, forKey: Key.refreshToken)   // 먼저
            try store.set(tokens.accessToken, forKey: Key.accessToken)
        } catch {
            removeTokens()
            throw error
        }
    }
}
저장 순서두 번째 쓰기와 되돌리기가 모두 실패하면 남는 값그다음
Refresh 먼저 (지금)새 Refresh + 옛 Access옛 Access가 만료되면 새 Refresh로 갱신해요. 세션이 이어져요
Access 먼저새 Access + 옛 Refresh회전으로 옛 Refresh는 이미 폐기됐어요. Access가 만료되면 갱신이 실패해서 다시 로그인해야 해요

UserDefaults로 바꾼 뒤에는 removeTokens()가 실패하지 않아서, "되돌리기까지 실패"하는 상황은 일어나지 않아요. 문자열 저장도 사실상 실패하지 않아요. 그래서 이 상황을 만들던 테스트(keepsNewRefreshTokenWhenRollbackFails)는 지웠어요. 저장 순서와 주석은 코드에 그대로 있어요. Keychain처럼 삭제가 실패할 수 있는 저장 수단으로 바꾸면 이 순서가 다시 의미를 가져요.

20Store와 Storage 두 층

LocalStorage는 두 층으로 나뉘어요.

층위치아는 것타입
저장 수단 StoreLocalStorage/Store/어디에 어떻게 저장할지Storing·UserDefaultsStore, KeychainStoring·KeychainStore(지금은 쓰지 않음)
용도별 저장소 StorageLocalStorage/Storage/<용도>/무엇을 어떤 키와 타입으로 저장할지AuthTokenStorage, LocalSessionStorage, PushTokenStorage, RecentSearchStorage, DeepLinkStorage

Storage는 Store를 생성자로 받아 쓰고, Store의 protocol을 채택하지 않아요. 앱 코드는 Storage 층만 써요. reducer는 UserDefaults나 Keychain에 직접 접근하지 않아요(dependency-injection.md).

Storage/AuthToken/AuthTokenStorage.swift 
enum Key {
    static let accessToken = "auth.accessToken"
    static let refreshToken = "auth.refreshToken"
    static let signupToken = "auth.signupToken"
}

private let store: Storing

public init(store: Storing = UserDefaultsStore()) {
    self.store = store
}
Store/Storing.swift · Store/Keychain/KeychainStoring.swift 
public protocol Storing: Sendable {
    func value<T>(forKey key: String) -> T?
    func set<T>(_ value: T, forKey key: String) throws
    func removeValue(forKey key: String)
}

public protocol KeychainStoring: Sendable {
    func value(forKey key: String) throws -> String?
    func set(_ value: String, forKey key: String) throws
    func removeValue(forKey key: String) throws
}

왜 protocol이 둘인가요

  • 실패 모양이 달라요. Keychain은 읽기와 삭제가 실패할 수 있어서 throws가 필요해요. UserDefaults는 저장만 실패할 수 있어요(property list 타입이 아닐 때).
  • 다루는 타입이 달라요. KeychainStore는 문자열만 저장해요. UserDefaultsStore는 property list 타입을 저장하고, 아닌 타입은 unsupportedType 오류를 던져요. 토큰은 문자열이라 이 오류가 나지 않아요.
  • 지금 AuthTokenStorage는 Storing을 받아요. 그래서 KeychainStore를 그대로 넣을 수는 없어요. Keychain으로 되돌리려면 store의 타입을 KeychainStoring으로 바꾸고, try가 빠진 읽기·삭제 호출을 다시 고쳐야 해요.
  • 테스트가 쉬워요. 테스트는 Storing을 채택한 메모리 저장소(Tests/Support/InMemoryStore.swift)를 써요. failingKeys에 넣은 키에 저장하면 SaveError를 던져서 저장 실패만 만들 수 있어요. 읽기·삭제는 UserDefaults처럼 실패하지 않아요.

UserDefaultsStore의 선택

  • 기본값은 UserDefaults.standard예요. 토큰 키는 다른 설정과 섞이지 않게 auth.로 시작해요.
  • set에 nil을 넘기면 키를 지워요. property list 타입이 아니면 저장하지 않고 오류를 던져요.

남아 있는 KeychainStore

  • generic password 항목으로 저장하고, service 기본값은 com.poppang.auth예요. set은 먼저 SecItemUpdate를 시도하고, 항목이 없으면 SecItemAdd로 만들어요. 접근성 AfterFirstUnlockThisDeviceOnly는 새로 만들 때 지정해요.
  • 앱 코드는 이 타입을 쓰지 않아요. 직접 부르는 곳은 AuthTokenStorageTests의 실제 Keychain 테스트 하나뿐이에요.

222단계에서 연결한 것

1단계에서 만든 기반을 2단계에서 앱에 연결했어요. 소셜 로그인 흐름은 api-v2-migration.md의 2단계 절에 자세히 있어요.

연결한 것어떻게 했나요
NetworkProvider.shared에 AuthenticationPlugin 연결갱신 API target(AuthTokenRefreshAPI)을 Data에 만들고, AppBootstrap이 토큰 저장소·refresher·plugin을 만들어 configureAuthentication(_:)으로 요청 전에 넣어요. 갱신 API는 plugin이 없는 provider로 불러서 갱신 요청에 다시 갱신이 걸리지 않아요.
AuthSessionError.loginRequired를 받으면 로그인 화면으로plugin이 AuthSessionEvents로 알리고(구독할 때마다 새 stream을 줘요), AppFeature가 메인 화면에서만 로그아웃 전환을 해요. 로그인 화면이나 로그아웃 중에 온 알림은 무시해요.
로그인·가입 토큰 저장AuthRepositoryImpl이 COMPLETED면 토큰 쌍을, PENDING이면 Signup Token을 저장해요. 가입에 성공하면 토큰 쌍을 저장하고 Signup Token을 지워요. 토큰은 feature에 넘기지 않아요.
앱 시작 세션 복구autoLogin 대신 저장된 토큰으로 내 정보 조회(GET /api/v2/user)를 불러요. 만료됐으면 이 문서의 갱신 흐름이 그대로 동작해요.
로그아웃서버 로그아웃(POST /api/v2/auth/logout)을 부른 뒤, 실패해도 기기의 토큰을 지워요. 토큰이 없으면 서버에 묻지 않아요.
재설치 시 Keychain 정리할 필요가 없어졌어요. 토큰을 UserDefaults로 옮겨서 앱을 지우면 세션과 토큰이 함께 지워져요(9절).

23복습 질문

답을 먼저 떠올린 뒤 펼쳐 보세요.

1. JWT payload에 사용자 이메일을 넣어도 안전할까요?

아니요. Base64URL은 인코딩이라 누구나 디코딩해서 읽어요. 서명은 위조를 막을 뿐 내용을 숨기지 않아요.

2. Access Token만 길게 쓰면 안 되는 이유는 뭔가요?

요청마다 네트워크를 타서 새기 쉽고, 서명만으로 검증하면 중간에 무르기 어려워요. 짧게 살리고, 서버가 통제하는 Refresh Token으로 갱신해요.

3. PopPang이 401을 받았는데 코드가 5001이면 어떻게 되나요?

갱신하지 않아요. 보낸 토큰이 아직 저장된 토큰이면 지우고 loginRequired를 던져요. 그사이 다른 요청이 갱신했으면 지우지 않고 새 토큰으로 한 번만 다시 보내요. 토큰 없이 보낸 요청이면 토큰 쌍이 없을 때 남은 토큰을 지우고 loginRequired를 던져요. 그사이 로그인으로 쌍이 생겼으면 새 토큰으로 한 번만 다시 보내요.

4. 갱신 뒤 다시 보낸 요청이 또 5002를 받으면요?

다시 갱신하지 않고 그 오류를 던져요. 토큰은 지우지 않아요. 재요청은 구조상 한 번이에요.

5. 다섯 요청이 동시에 만료되면 갱신 API는 몇 번 불리나요? 무엇이 그렇게 만드나요?

한 번이에요. actor 안의 inFlightRefresh Task 하나를 나머지 요청이 기다려요. 갱신이 끝난 뒤 도착한 요청은 저장된 토큰이 보낸 토큰과 다르다는 것을 보고 갱신을 건너뛰어요.

6. 갱신하는 동안 로그아웃했어요. 늦게 온 성공 응답은 어떻게 되나요?

replaceTokens(_:ifRefreshTokenIs:)가 저장된 Refresh Token이 없어서 false를 돌려줘요. 저장하지 않고 loginRequired를 던져요.

7. 토큰 저장소를 Keychain으로 되돌린다면, 읽기 실패를 nil로 바꿔 돌려주면 무슨 문제가 생기나요?

잠금 해제 전 백그라운드 실행 같은 일시적인 상황에서 토큰이 없다고 판단해 사용자를 로그아웃시킬 수 있어요. 그래서 KeychainStoring은 읽기 실패를 오류로 던져요.

8. saveTokens가 Refresh Token을 먼저 쓰는 이유는요?

되돌리기까지 실패해 한쪽만 남을 때 새 Refresh Token이 남아야 다음 만료 때 갱신할 수 있어요. 반대 순서면 폐기된 옛 Refresh Token이 남아요. UserDefaults에서는 삭제가 실패하지 않아 이 상황이 생기지 않지만, 저장 수단이 바뀌어도 안전하도록 순서를 지켜요.

9. V1 target에 authorization = .access를 적으면요?

resolvedAuthorization이 .none을 돌려줘서 헤더도 붙지 않고 갱신 흐름에도 들어가지 않아요.

10. AuthTokenStorage의 lock이 static이고 recursive인 이유는요?

struct 인스턴스가 여러 개여도 실제 저장소(UserDefaults의 같은 키)는 하나라서 lock도 하나를 같이 써요. replaceTokens처럼 lock 안에서 다시 lock을 잡는 함수를 부르기 때문에 recursive여야 해요.

11. PopPang이 서버 명세의 Keychain 대신 UserDefaults에 토큰을 두는 이유와 대가는요?

앱을 지우면 토큰도 함께 지워져서, 재설치한 뒤 이전 계정 토큰이 남는 문제가 없어요. 대가로 암호화하지 않은 plist에 토큰이 남아 백업이나 탈옥 기기에서 노출될 수 있어요. 서버 명세와 다른 팀 결정이에요.
