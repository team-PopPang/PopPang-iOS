# PopPang 한국어 윤문 원칙

독자가 필요한 정보를 찾고, 다음에 할 일이나 검토 여부를 판단할 수 있게 글을 다듬어요. 문서의 목적을 먼저 정하고 정보 구성과 문장을 차례로 점검해요. 원문의 의미와 사실은 지켜요. 이 원칙을 작성자를 판별하거나 탐지 도구를 우회하는 데 쓰지 않아요.

## 함께 보는 문서

| 문서 | 언제 읽나요 |
| --- | --- |
| [문체](korean-editing/tone.md) | 해요체로 쓰거나, `-다`·`-습니다` 문장을 해요체로 바꿀 때 |
| [문서 유형 정하기](korean-editing/document-types.md) | 새 문서를 쓰거나, 문서의 성격이 애매할 때 |
| [정보 구조 만들기](korean-editing/information-structure.md) | 목차, 제목, 개요를 고치거나 문서를 나눌 때 |
| [문장 다듬기](korean-editing/sentences.md) | 문장을 고칠 때 |
| [문서 윤문 예시](examples/korean-editing-examples.md) | 문장의 주체·조건을 분명히 하거나 문서 흐름을 정리한 전후 비교가 필요할 때 |
| [PR 작성 예시](examples/pr-writing-examples.md) | 변경 규모에 맞춰 PR 제목과 본문을 쓸 때 |
| [Git 작업 흐름](gitflow.md) | 커밋과 PR을 만드는 절차를 확인할 때 |

문체, 문서 유형, 정보 구조, 문장 다듬기 문서는 PopPang-Docs의 [`poppang-technical-writing`](https://github.com/team-PopPang/PopPang-Docs/tree/main/.agents/skills/poppang-technical-writing) 스킬 내용을 PopPang-iOS 기준에 맞춰 옮겼어요.

## 적용 범위

- `README.md`, `AGENTS.md`, `CLAUDE.md`, `Docs/` 아래의 한국어 문서
- 작업 계획, 보고서처럼 저장소 안에서 쓰는 한국어 문서
- 이슈·PR 제목과 본문
- 사용자가 윤문을 요청한 Markdown·일반 텍스트 파일

## 문체

PopPang 글은 해요체로 써요. 해요체로 쓰고 바꾸는 방법은 [문체](korean-editing/tone.md)를 봐요.

| 대상 | 문체 |
| --- | --- |
| 사람이 읽는 문서(`Docs/`, `README.md`) | 해요체 |
| PR·이슈 본문 | 해요체. 변경 사항 bullet은 `- ...했어요.`로 쓰고, 상세 설명 문단도 해요체로 써요. ([PR 작성 스타일](../../.agents/skills/auto-pr/references/pr-writing-style.md)) |
| 이슈·PR 제목 | `[type] 한글 설명`으로 쓰고 `-다`로 끝내요. 예: `[fix] 프로필 닉네임 변경 후 홈 헤더가 갱신되지 않는 문제를 해결한다` |
| 커밋 메시지 | `type: 한글 설명`. 명사형과 `-다`를 모두 써요. ([Git 작업 흐름](gitflow.md)) |
| AI 지침(`AGENTS.md`, `CLAUDE.md`, `.agents/skills/` 문서) | `-다` 체. 판단 기준을 또렷하게 하려고 지시문으로 써요. |
| 표·목록·체크리스트 | 명사형 끝맺음(개조식)도 써요. |
| 직접 인용, 원문을 지킬 프롬프트 | 원문 어미를 그대로 둬요. |

이미 있는 글을 윤문할 때는 원문의 해요체·합쇼체·한다체를 그대로 둬요. 문서를 새로 쓰거나 전체를 다시 쓸 때, 사용자가 문체 통일을 요청했을 때만 해요체로 바꿔요. 한 결과물 안에서는 어미를 섞지 않아요. 지금 `Docs/`에 남은 `-다` 체 문서는 전체를 고칠 때 문서 단위로 해요체로 바꿔요.

## 사실의 근거

- 프로젝트 문서에는 `Projects/` 아래 코드와 저장소 설정에서 확인한 내용만 써요. `Legacy/`와 `Docs/etc/`의 내용을 근거로 옮겨 적지 않아요.
- 확인하지 못한 내용은 단정하지 않고, `확인 필요`와 확인할 파일·명령을 적어요.
- 문장을 구체적으로 만들려고 동작, 수치, 성과를 새로 만들지 않아요.

## 작업 범위와 독자의 목적

문장 윤문, 내용 재구성, 새 초안 작성은 적용 범위가 달라요. 기존 초안을 줄여 달라는 요청이 없는데 사실을 지우거나, 새 PR에 작업 기록 전체를 옮기지 않아요.

| 요청 | 적용 범위 |
| --- | --- |
| 기존 문장을 다듬어요. | 의미·정보량·구조를 유지하고 어색한 표현만 고쳐요. |
| 요약하거나 구성을 바꿔요. | 허용한 범위에서 중복을 합치고 순서를 바꿔요. 조건·제약·검증 결과는 지켜요. |
| 문서나 PR을 새로 써요. | 확인한 자료에서 독자의 판단에 필요한 사실을 골라 구성해요. 모든 자료를 본문에 넣을 필요는 없어요. |

독자가 이 글에서 해결하려는 질문 하나를 정해요. 유형마다 꼭 넣을 것과 피할 것은 [문서 유형 정하기](korean-editing/document-types.md)를 봐요.

| 독자의 질문 | 문서 유형 | 먼저 전할 정보 | PopPang 예 |
| --- | --- | --- | --- |
| 처음 어떻게 시작하나요? | 시작하기 가이드 | 목표, 사전 조건, 최소 실행 절차, 결과 확인 | [Tuist 설치와 실행](tuist.md) |
| 따라 만들며 배우려면 어떻게 하나요? | 튜토리얼 | 목표, 단계별 진행, 실행할 수 있는 예제, 결과 확인 | |
| 지금 생긴 문제를 어떻게 해결하나요? | 문제 해결 가이드 | 증상·발생 조건, 확인한 원인, 조치, 정상 여부 확인 | `tuist.md`의 문제 해결 |
| 어떤 규칙이나 계약을 쓰나요? | 참조 문서 | 의미, 허용값·기본값, 입출력, 제한사항 | [Swift 스타일](swiftstyle.md) |
| 왜 이 구조를 골랐나요? | 설명 문서 | 문제, 판단 근거, 필요한 대안 비교, 한계 | [TCA Navigation](../architecture/tca-navigation.md) |
| 이 변경을 병합해도 되나요? | PR 설명 | 변경 이유와 전후 동작, 검증, 판단에 필요한 영향 | [PR 작성 예시](examples/pr-writing-examples.md) |

유형별 항목은 확인할 정보이고, 모든 문서에 그대로 붙이는 필수 목차가 아니에요. 내용이 짧으면 별도 제목 없이 한 문단에 담아요.

## 핵심부터 배치하기

새 초안을 쓰거나 구조 변경을 요청받았을 때 이 기준을 적용해요. 문장 윤문만 요청받았다면 구조 문제는 별도 제안으로 남겨요. 자세한 기준과 예는 [정보 구조 만들기](korean-editing/information-structure.md)를 봐요.

- 첫 문단에서 해결할 문제나 달라지는 동작을 밝혀요. 작업을 시작한 경위나 도구 실행 순서로 도입을 채우지 않아요.
- 한 페이지에는 주된 목적 하나를 둬요. 긴 배경이나 별도 절차는 필요하면 다른 문서로 연결해요.
- 제목에는 대상과 행동·결과를 써요. `기타`, `개선 사항`처럼 내용이 드러나지 않는 제목은 피해요.
- 실행 절차는 사전 조건과 정상 결과를 함께 적어요.
- 독자가 모를 개념은 처음 나올 때 짧게 설명해요. 상태·입력·환경에 따라 결과가 달라지면 그 조건을 남겨요.
- 같은 사실을 개요, 변경 목록, 결론에서 반복하지 않아요.

주체나 조건이 불명확하면 코드에서 확인해요. 확인할 수 없는 `일부 환경`을 임의의 OS나 버전으로 바꾸지 않고, `발생할 수 있다`를 `발생한다`로 단정하지 않아요.

## PR 쓰기

PR 제목과 본문은 최종 diff와 실제 검증 결과로 써요. 제목은 연결된 이슈 제목과 같게 써요.

| 변경의 성격 | 필요한 설명 |
| --- | --- |
| 오탈자·링크·작은 문서 수정 | 대상과 수정 이유를 한두 bullet로 설명하고 실제 확인 결과를 덧붙여요. |
| 버그 수정·일반 기능 변경 | 발생 조건과 전후 동작을 설명하고 관련 검증을 적어요. 원인이 중요하면 `### 문제 원인`, `### 해결 내용`, `### 검증한 내용`을 더해요. |
| 공유 모듈·public protocol·navigation에 영향을 주는 변경 | 선택 근거와 영향 범위를 더해요. 적용 순서나 남은 확인이 있으면 밝혀요. |

이 표는 분량의 상한이나 필수 섹션 수를 정하지 않아요. 리뷰어가 결론을 판단할 수 있으면 멈추고, 짧게 쓰느라 중요한 제약이나 실패를 숨기지 않아요.

1. `.github/PULL_REQUEST_TEMPLATE.md`의 섹션과 순서를 유지해요: `💡 PR 유형`, `✏️ 변경 사항`, `🚨 관련 이슈`, `🎨 스크린샷`, `✅ 체크리스트`, `🔥 추가 설명`.
2. 변경 사항에는 무엇이 어떻게 달라졌는지 써요. 상세 목록은 서로 다른 동작이나 검토 지점을 구분할 때만 늘려요.
3. 파일 목록, 커밋 순서, 작업 중 시도, diff로 바로 보이는 변경을 그대로 나열하지 않아요. 설계 이유를 이해하는 데 필요한 구현 세부사항은 남겨요.
4. 검증은 실행한 명령·시나리오와 결과를 적어요. 실행하지 못한 중요한 검증과 이유도 밝혀요. 문서만 고쳤다면 앱 테스트를 통과했다고 쓰지 않아요.
5. 체크리스트는 실제로 확인한 항목만 체크해요.
6. 제목·변경 사항·추가 설명의 중복을 정리하고 [AI 작성 표기 규칙](ai-attribution.md)도 확인해요.

## 필수 원칙

1. 의미를 바꾸지 않아요.
   - 사실, 주장, 인과관계, 조건, 긍정·부정 유지
   - 수치, 날짜, 단위, 버전, 고유명사 유지
2. 필자의 말투와 문서 장르를 바꾸지 않아요.
   - 해요체·합쇼체·한다체 유지. 문서 전체를 다시 쓰거나 문체 통일을 요청받았을 때만 해요체로 바꿈
   - 기술 문서를 홍보 문구나 구어체로 바꾸지 않음
3. 문제가 확인된 구간만 고쳐요.
   - 이미 자연스러운 문장 유지
   - 문서 전체를 같은 모양으로 재작성하지 않음
4. 정보량과 논리 단계를 유지해요.
   - 요약·삭제 요청이 없으면 내용 생략 금지
   - 가능성을 단정으로, 조건을 무조건으로 바꾸지 않음
5. 보호 구간을 그대로 둬요.
   - 직접 인용, 원문 보존을 요청한 프롬프트, 코드, 명령, 경로, URL, 이미지, 각주 보존
6. 새로운 주장이나 수사를 넣지 않아요.
   - 원문에 없는 비유, 경험, 성과, 수치 추가 금지
   - `혁신적인`, `획기적인`, `의미가 크다` 같은 상투구 추가 금지

## 윤문 전에 정할 것

| 항목 | 기록할 내용 |
| --- | --- |
| 장르와 독자 | 기술 문서, 계획, PR 등 문서의 역할과 주요 독자 |
| 목적과 작업 범위 | 독자의 질문, 문장 윤문·재구성·새 초안 중 허용한 작업 |
| 원래 말투 | 지배적인 종결어미와 격식 수준 |
| 보호 요소 | 수치, 이름, 링크, 인용, 코드, 표, 이미지 위치 |
| 핵심 정보 | 반드시 남겨야 할 주장, 조건, 인과관계 |
| 수정 강도 | 보수적, 기본, 정밀 중 하나 |

파일을 직접 수정할 때는 Git diff로 원문과 대조할 수 있게 해요. 관련 없는 변경과 다른 사람이 쓴 내용은 건드리지 않아요.

## 수정 강도

| 강도 | 적용 기준 | 수정 범위 |
| --- | --- | --- |
| 보수적 | 이미 자연스러운 글, 일부 문장만 고치는 요청 | 분명한 번역투와 상투구만 수정 |
| 기본 | 일반적인 초안, 별도 강도 지정 없음 | 지배적인 문제 3~6개를 중심으로 수정 |
| 정밀 | 문서 전체, 긴 글, 구조가 복잡한 글 | 진단·윤문·원문 대조를 나누어 수행 |

변경량을 목표로 삼지 않아요. 손댈 곳이 거의 없으면 억지로 표현을 바꾸지 않아요.

## 진단 기준

표현 하나만 보고 기계적인 문체라고 단정하지 않아요. 문맥에 맞지 않거나 같은 패턴이 반복될 때만 수정 후보로 봐요. 항목별 예는 [문장 다듬기](korean-editing/sentences.md)를 봐요.

| 진단 항목 | 확인할 패턴 | 수정 방향 |
| --- | --- | --- |
| 주체와 행동 | 누가 무엇을 하는지 드러나지 않는 문장 | 확인한 주체와 행동을 직접 쓰고, 근거 없는 주체는 추가하지 않음 |
| 문장별 핵심 | 한 문장에 서로 다른 조건·결과가 몰림 | 한 문장에 핵심 하나를 두되 조건과 인과관계 유지 |
| 용어 일관성 | 같은 개념의 이름·약어·대소문자가 달라짐 | 코드 식별자와 공식 표기를 보존하며 같은 개념은 같은 말로 표현 |
| 번역투와 피동 | `X에 대해`, `X를 통해`, 이중 피동, 추상 주어 | 자연스러운 조사와 구체적인 동사 사용 |
| 영어와 전문 용어 | 불필요한 영어 병기, 광고성 영어 | 필요한 첫 등장만 병기, 통용되는 기술 용어 유지 |
| 기계적인 구조 | 같은 순서의 접속사·대구·불릿 반복 | 정보 구조에 필요한 목록만 유지 |
| 상투구와 과장 | `결론적으로`, `주목할 만하다`, 빈 칭찬 | 삭제하거나 원문에 있는 사실과 직접 연결 |
| 명사화와 중복 | `~적·~성·~화`, 겹치는 수식어 | 동사와 형용사로 직접 표현 |
| 완곡 표현 | 가능성 표현과 피동의 중첩 | 원문의 불확실성을 유지하며 중복만 제거 |
| 접속사와 메타 문장 | `또한`, `따라서`, `이는`의 반복 | 논리 관계가 분명하면 생략 |
| 형식명사와 빈 결말 | `것·점·수·바`, 같은 결론 반복 | 핵심 내용을 직접 서술 |
| 시각 장식 | 과도한 볼드, 따옴표, 대시, 이모지 | 문서 구조에 필요한 장식만 유지. PR 템플릿의 섹션 이모지는 유지 |

## 수정 순서

1. 문서 전체를 읽고 독자의 목적, 작업 범위, 말투와 보호 요소를 확인해요.
2. 글을 지배하는 문제 3~6개만 골라요.
3. 빈 결론, 과장, 메타 문장을 지우거나 원문 사실에 연결해요.
4. 번역투, 이중 피동, 추상 주어를 자연스러운 조사와 동사로 바꿔요.
5. 형식명사, 명사화, 중복 수식, 과도한 완곡 표현을 줄여요.
6. 기계적인 접속사, 대구, 불릿, 강조를 정리해요.
7. 앞뒤 문단의 용어와 말투를 맞춰요.
8. 원문과 윤문본을 직접 대조해요.

항상 문단 단위로 읽어요. 문장 하나를 자연스럽게 만들려고 앞뒤의 논리 연결을 끊지 않아요.

## PopPang 문서에서 지킬 선

- Swift 타입, 프로토콜, 메서드, 프로퍼티, action case 이름의 원형 유지 (`MainTabFeature`, `popupSelected(Popup)`, `userUuid`)
- TCA, PopPangListKit, Tuist, Moya 같은 제품·라이브러리 이름 원형 유지
- Tuist target, scheme, bundle id, 파일 경로 원형 유지
- 철자가 틀린 기존 이름(`getPersonalUseerRecommendPopupList`, section id `"comming"`)을 문서에서 임의로 고치지 않음
- 오류 메시지와 로그 원문 유지
- 코드 예제와 명령의 동작을 문체 수정 과정에서 바꾸지 않음
- `Projects/` 코드로 확인하지 않은 동작이나 성과 추가 금지

전문 용어를 모두 쉬운 말로 바꾸지 않아요. 독자에게 설명이 필요하면 처음 나오는 곳에만 짧게 덧붙여요.

## 원문 대조

윤문을 마친 뒤 아래 항목을 확인해요.

- 빠지거나 새로 생긴 정보가 없나요?
- 인과관계와 조건이 유지되나요?
- 가능성과 추정이 단정으로 바뀌지 않았나요?
- 수치, 이름, 인용, 링크, 코드가 그대로인가요?
- 제목, 표, 목록, 이미지 위치가 의도치 않게 바뀌지 않았나요?
- 원래 말투보다 딱딱하거나 가벼워지지 않았나요? 해요체로 바꾸기로 한 경우에도 격식 수준은 맞춰요.
- 모든 문장이 짧거나 같은 모양으로 다시 정렬되지 않았나요?

변경량이 30% 이상이면 정보 누락과 말투 변화를 다시 확인하고, 50% 이상이면 문단별로 원문과 대조해 문제가 있는 구간을 되돌려요. 변경률은 경고 기준이고 목표가 아니에요.
