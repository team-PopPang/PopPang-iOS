# 문서 유형 정하기

문장을 고치기 전에 문서 유형부터 정해요. 유형이 정해지면 구조, 예시, 설명의 깊이를 한 방향으로 맞출 수 있어요. 기준은 "무엇을 쓰고 싶은가"가 아니라 "독자가 이 문서를 왜 여는가"예요.

## 고르기 전에 답할 질문

1. 독자가 문서를 열자마자 원하는 것은 무엇인가요? 빨리 시작하기, 따라 만들기, 지금 생긴 문제 풀기, 옵션이나 API 확인하기, 원리 이해하기 가운데 무엇인지 봐요.
2. 독자는 이미 무엇을 알고 있나요? 처음 보는 사람인지, 기본 흐름은 아는 사람인지, 특정 문제만 풀면 되는 사람인지 봐요.
3. 다 읽은 뒤 독자는 무엇을 하나요? 설치, 따라 만들기, 오류 해결, 구현에 적용, 결정 가운데 무엇인지 봐요.
4. 이 문서에서 가장 중요한 것은 무엇인가요? 학습 경험, 해결 속도, 정확성과 완전성, 배경과 맥락 가운데 무엇인지 봐요.

판단이 애매하면 독자가 문서를 열자마자 가장 먼저 원하는 것을 기준으로 정해요.

## 유형 고르기

유형마다 먼저 전할 정보와 PopPang 예는 [한국어 윤문 원칙의 표](../korean-editing.md#작업-범위와-독자의-목적)에 있어요. 아래에서는 유형마다 꼭 넣을 것과 피할 것을 자세히 봐요.

## 학습을 위한 문서

독자가 새 기술이나 도구를 익히게 도와요. 이 문서를 따라 하면 무엇을 할 수 있는지 독자가 선명하게 그릴 수 있어야 해요.

- **시작하기 가이드**: 가장 빠른 입문에 집중해요. 짧아도 돼요. 독자가 "작동했다"를 빨리 경험하게 해요.
- **튜토리얼**: 하나를 따라 만들면서 이해하게 해요. 지식 전달보다 학습 경험을 설계하는 게 중요해요.

꼭 넣을 것은 목표, 사전 요구사항, 단계별 진행, 실행할 수 있는 예제, 결과 확인, 자주 막히는 문제예요.

- 쉬운 예제에서 시작해 점점 넓혀요.
- 단계마다 무엇을 왜 하는지 함께 적어요.
- 독자가 결과를 확인할 기준을 줘요.
- 단계가 크면 나눠요.

이런 문서는 다시 봐요: 목표가 모호해요. 설치나 설정이 빠졌어요. 예제가 실행되지 않아요. 배경 설명이 길어 시작이 늦어요. 결과를 확인할 방법이 없어요.

## 문제 해결을 위한 문서

독자가 지금 겪는 문제를 빨리 풀게 도와요. 이 문서를 보면 바로 해결할 수 있는지가 핵심이에요.

- **트러블슈팅**: 증상, 원인, 해결 순서, 확인 방법을 정리해요.
- **How-to 가이드**: 특정 작업을 끝내는 절차를 안내해요.
- **오류 코드·메시지 설명**: 오류의 뜻, 원인, 관련 링크를 정리해요.

독자가 원인 분석을 원하는지, 작업 절차를 원하는지 먼저 구분해요. 꼭 넣을 것은 문제 정의, 증상이나 재현 조건, 원인, 해결 절차, 환경별 차이, 해결 후 확인 방법이에요.

- 오류 메시지는 원문 그대로 보여 줘요.
- 복사해서 바로 쓸 수 있는 명령과 코드를 줘요.
- 해결책이 왜 통하는지 짧게 설명해요.
- OS, 버전, 환경에 따라 달라지는 조건을 함께 적어요. 확인하지 못한 조건은 `확인 필요`로 남겨요.

이런 문서는 다시 봐요: 원인 없이 해결책만 있어요. 해결 순서가 모호해요. 예제가 실행되지 않아요. 무엇이 정상인지 알려 주지 않아요. 배경 설명에 핵심 조치가 묻혀요.

## 참조를 위한 문서

정확하고 완전한 정보를 빨리 찾게 해요. 정확성, 완전성, 찾기 쉬운 구조가 핵심이에요.

꼭 넣을 것은 개요, 시그니처나 핵심 인터페이스, 매개변수·속성 표, 반환값, 사용 예제, 주의사항과 제한사항이에요.

- 모든 항목을 같은 순서로 써요.
- 예제는 짧고 바로 쓸 수 있게 해요.
- 용어, 표기, 표 구조를 문서 전체에서 맞춰요.
- 찾아갈 수 있는 제목을 써요.

이런 문서는 다시 봐요: 속성 설명이 빠졌어요. 허용하는 값이 모호해요. 예제보다 설명이 길어요. 페이지마다 표 구조가 달라요.

## 깊은 이해를 위한 문서

기술이나 개념, 설계 판단을 깊게 이해하게 해요. 배경과 맥락을 충분히 주고, 결정 이유를 숨기지 않는 게 핵심이에요.

꼭 넣을 것은 개념 소개, 등장 배경, 해결하려는 문제, 작동 원리, 대안 비교, 실제 활용이에요.

- 배경과 맥락을 앞에 둬요.
- 결정 이유를 숨기지 않아요.
- 장점과 한계를 함께 적어요.
- 필요하면 표나 흐름도를 써요.

이런 문서는 다시 봐요: 원리 없이 결론만 있어요. 비교 기준이 없어요. 장점만 있고 한계가 없어요. 왜 중요한지 알 수 없어요.

## 유형을 섞을 때

한 페이지의 주된 목적은 하나여야 해요. 다른 유형의 요소를 조금 섞을 수는 있지만, 독자가 이 페이지를 연 이유를 흐리면 안 돼요.

| 섞어도 좋아요 | 섞으면 안 돼요 |
| --- | --- |
| 시작하기 가이드 끝의 짧은 FAQ | 입문 문서 안의 긴 API 목록 |
| How-to 가이드의 세부 옵션을 참조 문서로 분리 | 트러블슈팅 앞의 긴 배경 설명 |
| 설명 문서 안의 짧은 확인용 예시 | 절차로만 채운 설명 문서 |

## 유형별 뼈대

새 문서를 쓸 때 출발점으로 써요. 내용이 짧으면 제목 없이 한 문단에 담아도 돼요.

**학습 중심 문서**

```markdown
# [문서 제목]

## 목표
[이 문서를 마치면 할 수 있는 일]

## 사전 요구사항
- [필요한 도구, 계정, 버전]

## 빠른 개요
[전체 흐름을 2~4문장으로]

## 단계별 가이드
### 1. [첫 단계]
[무엇을 왜 하는지]

## 결과 확인
[정상 결과]

## 자주 막히는 문제
```

**문제 해결 중심 문서**

```markdown
# [문제나 작업 제목]

## 문제 정의
## 증상 또는 목표
## 원인 또는 배경
## 해결 방법
### 1. [첫 번째 조치]
## 확인 방법
```

**참조 문서**

```markdown
# [API나 기능 이름]

## 개요
## 시그니처
## 매개변수
| 이름 | 타입 | 기본값 | 설명 |
| --- | --- | --- | --- |
## 반환값
## 예제
## 주의사항
```

**설명 문서**

```markdown
# [개념 이름]

## 이 문서에서 설명하는 것
## 등장 배경
## 해결하려는 문제
## 작동 원리
## 비교
## 실제 활용
```

## 확인할 것

- 독자의 목표가 분명한가요?
- 주된 유형이 하나로 정리되나요?
- 가장 중요한 경험이 학습, 해결, 참조, 이해 가운데 무엇인지 분명한가요?
- 다른 유형의 요소가 핵심 목적을 흐리지 않나요?
