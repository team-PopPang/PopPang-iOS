# 문장 다듬기

문장을 다듬는 일은 줄이는 일이 아니에요. 뜻을 지키면서 더 분명하고 자연스럽게 만드는 일이에요. 구조가 좋아도 문장이 흐리면 독자에게 전달되지 않아요.

뜻이 흔들리면 더 짧게 만들 수 있어도 줄이지 않아요. 우선순위는 뜻 유지, 정보 정확성, 이해 속도, 문장 길이, 톤 일관성 순서예요.

## 다듬는 순서

1. 문장의 주체가 누구인지 봐요.
2. 한 문장에 생각이 몇 개 들어 있는지 봐요.
3. 명사형 표현을 동사로 바꿔요.
4. 번역투와 어색한 한자어를 정리해요.
5. 같은 개념이 다른 말로 섞였는지 봐요.

이 순서를 따르면 짧아졌는데 뜻이 흐려지는 실수를 줄일 수 있어요.

## 주체를 분명하게 써요

누가 무엇을 하는지 바로 보여야 해요.

- 행동하는 쪽을 주어로 써요. 사람이 할 일이면 독자나 개발자를, 코드가 하는 일이면 그 타입을 주어로 써요.
- 수동형보다 능동형을 써요.
- 근거 없는 주체를 새로 만들지 않아요. 코드에서 확인한 주체만 써요.

| 수정 전 | 수정 후 |
| --- | --- |
| `HomeFeature`에서는 팝업 목록 응답 결과에 대한 화면 상태로의 반영 처리를 수행한 후 로딩 종료를 진행해요. | `HomeFeature`가 팝업 목록 응답을 화면 상태에 반영하고 로딩을 끝내요. |

## 필요한 정보만 남겨요

한 문장에는 핵심 하나만 담아요.

- 긴 문장은 둘 이상으로 나눠요.
- 같은 사실을 개요, 목록, 결론에서 되풀이하지 않아요.
- 말에 대한 말인 메타 담화를 빼요. 예: `앞서 설명했듯이`, `이제 알아보겠습니다`, `다음과 같이 진행할 수 있습니다`, `결론적으로`

**수정 전**

> 이 API를 호출할 때 요청 헤더와 인증 정보를 포함해야 정상적으로 응답을 받을 수 있으며, 일부 환경에서는 타임아웃 설정도 필요할 수 있고, 응답 형식도 함께 확인해야 합니다.

**수정 후**

> 이 API를 호출할 때는 요청 헤더와 인증 정보를 넣으세요. 일부 환경에서는 타임아웃 설정이 필요할 수 있어요. 호출한 뒤에는 응답 형식을 확인하세요.

문장을 나눠도 `일부 환경`과 `필요할 수 있어요`는 그대로 뒀어요. 확인하지 않은 조건을 단정하지 않아요.

## 구체적으로 써요

독자가 지금 무엇을 해야 하는지, 무엇이 달라지는지, 어떤 조건에서 결과가 바뀌는지 바로 알 수 있어야 해요.

- 명사 대신 동사를 써요.
  - 수정 전: 코드 최적화 진행 후 배포 수행이 필요해요.
  - 수정 후: 코드를 최적화한 뒤 배포하세요.
- 필요한 맥락을 문장 안에 넣어요.
  - 수정 전: 준비한 뒤 생성하세요.
  - 수정 후: `./scripts/download-rn-release.sh v1.0.0`으로 React Native 산출물을 받은 뒤 `tuist generate`를 실행하세요.
- 모호한 표현은 확인한 사실로만 바꿔요. `일부 브라우저`를 특정 브라우저로, `영향을 받을 수 있다`를 `삭제된다`로 바꾸려면 코드나 실행 결과로 확인해야 해요. 확인하지 못했으면 가능성 표현을 남기고 `확인 필요`와 확인할 대상을 적어요.

## 자연스러운 한국어로 써요

- 뜻 없이 붙은 `수행하다`, `진행하다`, `처리하다`와 불필요한 한자어를 줄여요.
  - 수정 전: 로그 파일을 삭제하는 작업을 수행해요.
  - 수정 후: 로그 파일을 삭제해요.
- 번역투를 풀어요. `~에 대해`, `~를 통해`, `~에 의해`, `되어지다` 같은 표현을 살펴봐요.
  - 수정 전: API 키를 이용한 사용자 인증 처리가 완료된 후, 데이터베이스 접속 설정 진행이 가능해요.
  - 수정 후: API 키로 사용자를 인증한 뒤 데이터베이스 접속을 설정할 수 있어요.
- 군더더기를 빼요.
  - 수정 전: 다음과 같은 방식으로 설정을 진행할 수 있어요.
  - 수정 후: 이렇게 설정하세요.
- 소리 내어 읽었을 때 어색하면 고쳐요.

## 일관되게 써요

같은 개념을 여러 말로 쓰면 독자가 헷갈리고 검색도 어려워져요.

- 공식 용어와 표기를 따라요. 코드 식별자와 제품 이름은 원형 그대로 써요. 예: `MainTabFeature`, Tuist, TCA
- 같은 개념은 한 문서 안에서 같은 말로 써요. `추가`, `첨부`, `넣기`를 섞어 쓰지 않아요.
- 약어는 처음 나올 때 풀어 써요. 예: `서버 사이드 렌더링(Server-Side Rendering, SSR)`. 팀에서 늘 쓰는 약어는 그대로 둬도 돼요.
- 대소문자까지 맞춰요.

## 한 문단을 다듬는 예

**수정 전**

> 이 기능을 사용하기 위해서는 인증 설정 진행 후 요청 헤더 값 세팅을 수행해야 하며 일부 상황에서는 응답값이 다르게 내려올 수 있습니다.

**수정 후**

> 이 기능을 쓰려면 먼저 인증을 설정하세요. 그다음 요청 헤더 값을 넣으세요. 일부 상황에서는 응답 값이 다르게 올 수 있어요.

명사형 표현을 동사로 바꾸고, 생각마다 문장을 나눴어요. `일부 상황`이 어떤 경우인지 확인했다면 그 조건을 쓰고, 확인하지 못했다면 그대로 둬요.

## 확인할 것

- 주체가 분명한가요?
- 한 문장에 생각을 하나만 담았나요?
- 메타 담화가 남아 있지 않나요?
- 명사형보다 동사를 썼나요?
- 확인한 사실만 구체적으로 바꿨나요? 가능성 표현을 단정으로 바꾸지 않았나요?
- 한국어 어순과 표현이 자연스러운가요?
- 같은 개념을 같은 말로 썼나요?
