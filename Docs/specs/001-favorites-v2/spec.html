2번은 V2 API 마이그레이션의 feature별 전환 표의 2번 행이다.

순서 2 · FavoritesFeature · 찜 목록 (FAV-04), 찜 등록·해제 (FAV-01·02) · 예정

같은 문서의 원칙: 여러 feature가 같이 쓰는 API(찜 등록·해제 등)는 처음 쓰는 feature에서 V2로 만들고, 뒤의 feature는 가져다 쓴다. userUuid는 아직 V1인 화면이 쓰므로 마지막 정리 단계에서 지운다. PR은 feature마다 하나다.

1. 목표와 범위

왜 하는지

찜 탭이 부르는 V1 API 세 개를 V2로 옮긴다. V2는 userUuid를 경로·본문으로 받지 않고 Access Token의 사용자로 처리한다. 다른 사람의 userUuid로 찜을 바꿀 수 있던 V1의 구멍이 닫힌다.

하는 것

  • 찜 탭(FavoritesFeature)의 목록 조회, 찜 해제(하트 토글)를 V2로 부른다.
  • 찜 등록·해제 V2를 Domain·Data에 새로 만든다. 뒤의 feature가 가져다 쓴다.

하지 않는 것

  • 다른 feature(상세, 캘린더, 홈, 지도, 알림)의 찜 등록·해제 전환. 각자 차례에 옮긴다.
  • 찜 수 조회(FAV-03). 앱에 호출이 없다.
  • V1 찜 case와 Usecase의 userUuid 인자 삭제. 다른 feature가 아직 쓴다(9번 정리 단계).
  • 찜 탭 화면 디자인 변경.

성공 기준

  • 찜 탭이 V2 API 세 개만 부르고, 요청에 userUuid가 없다.
  • 찜한 팝업 목록, 빈 목록, 하트 토글이 V1 때와 같게 동작한다.
  • 로그인이 끊기면 다른 V2 화면처럼 로그인 화면으로 간다.

제약

  • feature 하나에 PR 하나. 다른 feature 동작을 바꾸지 않는다.
  • 명세 원문을 저장소에 옮기지 않는다(저장소가 공개, 명세는 내부용). 명세 ID와 앱에 필요한 사실만 적는다.
  • 승인 전 파일 수정 금지(AGENTS.md Plan-first).
  • 구현은 #131이 main에 병합된 뒤 main에서 새 이슈·브랜치로 시작한다. (1차 답)

2. 요구사항

  • R1 찜 탭은 찜한 팝업 목록을 GET /api/v2/favorite/popup(FAV-04)으로 받는다.
  • R2 찜 탭의 하트는 찜 해제를 DELETE /api/v2/favorite(FAV-02)로 보낸다. 본문은 popupUuid만 담는다. 찜 등록 POST /api/v2/favorite(FAV-01)는 Domain·Data에 만들어 두고 뒤의 화면이 쓴다. (찜 탭은 해제 전용으로 좁힘, 사용자 2026-10-28)
  • R3 찜 탭은 userUuid를 받지도 보내지도 않는다.
  • R4 찜 탭의 오류는 원본 오류 대신 정해 둔 안내 문구로 보여 준다. (1차 답)
  • R5 하트 토글이 이미 찜함(409 4101)·찜 없음(404 4102)으로 실패하면 안내 문구를 보여 주고 목록을 다시 받는다. (1차 답)

3. 현재 코드

  • 찜 탭 흐름: FavoritesFeature → FavoritesFeatureClient → PopupUsecase → PopupRepositoryImpl → PopupAPI(V1) (Projects/Features/FavoritesFeature/Sources/, Projects/Data/Sources/RepositoryImpl/PopupRepositoryImpl.swift)
  • V1 찜 API: getFavoriteList(userUuid:) GET /favorite/popup/{userUuid}, addFavorite·removeFavorite POST·DELETE /favorite 본문 {userUuid, popupUuid} JSON (Projects/Data/Sources/Remote/PopupAPI.swift:31-33, 73-76, 163)
  • FavoritesFeature.State는 userUuid를 들고 있고, 목록 조회와 토글에 쓴다. 토글 뒤에는 목록을 다시 받는다 (FavoritesFeature.swift)
  • 오류는 error.localizedDescription을 그대로 화면에 띄운다. V2 서버 오류면 응답 본문이 섞인 문장이 보인다 (FavoritesFeature.swift, FavoritesFeatureView.swift:91)
  • MainTabFeature가 .init(userUuid: user.userUuid)로 만든다. MainTabFeature.State.user가 있어 상세로 넘길 userUuid는 MainTab이 이미 안다 (MainTabFeature.swift:68, 81, 242)
  • addFavorite·removeFavorite Usecase는 상세, 캘린더, 홈, 오픈 예정 상세, 지도, 알림도 쓴다 (각 feature의 *Client.swift)
  • getFavoriteList는 찜 탭만 쓴다
  • FavoritesFeature에는 테스트 타깃이 없다 (Projects/Features/FavoritesFeature/Project.swift)
  • V2 기반: BaseAPI의 .v2·.access, asyncRequest(_:decodeDataTo:), asyncRequestVoid, AuthSessionError (Projects/Shared/Core/Sources/Network/)
  • 검색(#131) 선례: V2PopupAPI, PopupError.failed, popupRequest {}(AuthSessionError·취소는 그대로, 나머지는 로그 후 PopupError.failed), PopupDTO null 수정. #131은 아직 열려 있다(main 미병합)
  • 명세(FAV-04): 응답은 APIResponse로 감싼 팝업 배열이다(검색과 다름). 원소 필드는 V1과 같다
  • 명세(FAV-01·02): 성공은 200 본문 없음. 이미 찜함 409 4101, 찜 없음 404 4102. 명세는 이 둘을 성공으로 가정하지 말고 기존 오류 처리에 연결하라고 한다

5. 결정 기록

D-1 찜 탭 오류 문구

  • 결정: 원본 오류 대신 정해 둔 안내 문구 두 개(목록·토글)
  • 이유: V2 오류 본문이 화면에 보이지 않게. 검색(#131)과 같은 방식
  • 검토한 대안: 원본 오류 문장 유지
  • 영향: R4
  • 정한 사람: 사용자 (2026-10-27)

D-2 하트 토글 실패 뒤 목록 다시 받기

  • 결정: 토글이 실패하면 이유와 관계없이 안내 문구를 보여 주고 목록을 다시 받는다
  • 이유: 409 4101·404 4102는 서버 상태와 화면이 어긋났다는 뜻이라 다시 받아야 맞춰진다(사용자 답). 다른 실패도 다시 받아서 손해가 없고, 오류 코드를 구분할 새 오류 타입이 필요 없다
  • 검토한 대안: 4101·4102만 구분해 다시 받기(PopupError에 case 추가 필요)
  • 영향: R5
  • 정한 사람: 409·404 처리는 사용자 (2026-10-27). 모든 실패로 넓힌 것은 AI 제안, 사용자 확인 (2026-10-28 설계 승인)
  • 보완: D-5에서 로그인 끊김·취소는 다시 받지 않도록 좁혔다

D-3 V2 찜 API 위치

  • 결정: 새 파일 Data/Sources/Remote/V2FavoriteAPI.swift
  • 이유: 경로가 /favorite로 회원 팝업(/user/popups, V2PopupAPI)과 다르고, 명세도 다른 묶음(F)이다. 응답 래퍼도 다르다
  • 검토한 대안: V2PopupAPI에 case 추가(파일 하나지만 문서 주석의 "감싸지 않은 배열" 설명과 어긋남)
  • 영향: R1, R2
  • 정한 사람: AI 제안, 사용자 확인 (2026-10-28 설계 승인)

D-4 Domain 함수 모양

  • 결정: getFavoriteList(userUuid:)는 getFavoriteList()로 바꾼다(찜 탭만 씀). 등록·해제는 addFavorite(popupUuid:)·removeFavorite(popupUuid:)를 PopupRepositoryProtocol·PopupUsecaseProtocol에 새로 더하고 기존 userUuid 함수는 둔다
  • 이유: 기존 함수를 바꾸면 아직 V1인 다섯 feature가 같이 바뀐다. 전환 문서의 "처음 쓰는 feature에서 V2로 만들고 뒤의 feature가 가져다 쓴다" 원칙
  • 검토한 대안: 새 FavoriteRepository 분리(찜이 지금 Popup 저장소에 있어 이번 범위에 비해 큼)
  • 영향: R1, R2, R3
  • 정한 사람: AI 제안, 사용자 확인 (2026-10-28 설계 승인)

D-5 찜 해제는 낙관적으로 반영

  • 대체됨: D-6
  • 결정: 하트를 누르면 응답을 기다리지 않고 목록에서 먼저 뺀다. 해제가 성공하면 목록을 다시 받지 않는다. 실패하면 D-2대로 목록을 다시 받아 되돌리고 안내 문구를 보여 준다. 로그인 끊김(AuthSessionError)은 문구만 보여 주고 다시 받지 않으며, 취소는 아무것도 하지 않는다
  • 이유: push 전 리뷰가 두 가지를 지적했다. 응답을 기다리는 동안 같은 하트를 다시 누르면 두 번째 DELETE가 404 4102를 받아, 해제가 됐는데도 실패 문구가 뜬다. 로그인이 끊긴 뒤 목록을 다시 받으면 401이 한 번 더 나 "다시 로그인 필요" 알림이 두 번 간다
  • 검토한 대안: 요청 중에는 하트 탭을 무시(isLoading 조건), 그대로 두기(V1과 같은 서버 동작)
  • 영향: R5 / S01
  • 정한 사람: 사용자 (2026-10-28, "낙관적으로 진행")

D-6 숨길 팝업을 Set으로 들고 찜 탭 하트는 해제 전용

  • 대체됨: D-7 (Set 구성과 성공 뒤 다시 받기만. 찜 탭 해제 전용은 그대로)
  • 결정: 하트를 누르면 popupUuid를 해제 중 Set에 넣고 화면에서 숨긴다. 성공하면 해제 완료 Set으로 옮겨 다음 onAppear까지 숨긴다. 실패하면 Set에서 빼서 다시 보여 준다. 어떤 목록 응답이 와도 두 Set의 팝업은 빼고 보여 준다. 성공하면 목록을 다시 받지 않는다. 실패하면(로그인 끊김 제외) 목록을 다시 받는다. 목록 요청은 앞선 요청을 취소하고 가장 최근 응답만 반영한다. 목록 응답은 안내 문구를 지우지 않는다. 찜 탭 하트는 해제만 하고 찜 탭 Client에서 addFavorite를 뺀다
  • 이유: D-5로 push했을 때 리뷰가 지적했다. 해제 전에 보낸 목록 요청의 응답이 늦게 오면 먼저 뺀 팝업이 되살아나고, 한 팝업의 실패로 다시 받은 목록이 해제 중인 다른 팝업을 되살린다. 찜 탭의 팝업은 모두 찜한 팝업이라 등록 분기는 실행될 일이 없다
  • 검토한 대안: 해제가 끝나면 항상 목록을 다시 받기(요청이 늘고 그 응답도 늦을 수 있음), 등록 분기 유지
  • 영향: R2, R5 / S01
  • 정한 사람: 사용자 (2026-10-28, "Set으로, A로 진행". Set 방식은 사용자 제안)

D-7 해제 중 Set 하나와 성공 뒤 새로 받기

  • 결정: Set에는 해제 요청 중인 popupUuid만 둔다. 성공하면 Set과 서버 목록 사본(loadedPopups)에서 함께 빼고, 앞선 목록 요청을 취소한 뒤 목록을 새로 받는다. 실패하면 Set에서 빼서 다시 보여 주고 안내 문구를 띄운 뒤 목록을 새로 받는다(로그인 끊김은 다시 받지 않는다). 해제 요청이 취소되면 Set에서 빼서 다시 보여 주기만 한다. 목록 요청이 실패하면 언제나 목록 실패 문구를 보여 준다. 찜 탭 하트는 해제 전용(D-6)이고, V2 addFavorite(popupUuid:)는 뒤의 화면을 위해 Domain·Data에 남긴다(D-4)
  • 이유: D-6으로 push했을 때 리뷰가 지적했다. 해제 완료 Set을 onAppear에서 비운 뒤 목록 요청이 실패하면, 서버 목록 사본에 남아 있던 팝업이 다시 보인다. 해제 도중에 보낸 목록 요청은 해제 전 상태라 성공 뒤에 도착하면 팝업을 되살릴 수 있어, 성공 뒤 새로 받으며 그 요청을 취소한다
  • 검토한 대안: 성공 뒤 다시 받지 않고 진행 중이던 목록 요청이 있었을 때만 다시 요청(상태가 늘어 복잡함)
  • 영향: R2, R5 / S01
  • 정한 사람: 사용자 (2026-10-28, "A로, addFavorite는 남김")

6. 가정과 보류
